# @deepseek-ai/dsh-plan-model-switch

[English](README.md) | 中文

## 概述

有了 `dsh-plan-model-switch`，一个会话可以规划用一个模型、执行用另一个模型：进入计划模式时路由到规划模型，计划通过时路由到执行模型，产出计划的探索过程被折叠成一段摘要，因此执行阶段携带的是成果物而不是整份记录。当规划与执行的成本或能力画像不同时选择它。某一阶段只有同时配置了提供方与模型才会生效，因此未配置的部署与此前行为完全一致。`plan-execute` Agent 预设组合了本包；发布的 `standard` 预设没有。

<a id="use-this-package"></a>
## 使用本包

新建会话时选择 **计划/执行模式** 预设，然后在 **设置 › 插件 › 插件配置 › 规划与执行模型** 里选两个模型。两处都是下拉框，取自本部署已配置的模型目录（与模型页面同源）；模型若声明了推理强度，还会多一个强度下拉。之后就是普通流程：`/plan` 进入计划模式，审阅 Agent 通过 `exit_plan_mode` 提交的计划，批准它。模型正是在批准那一刻切换的。

### 何时选择

当两个阶段确实想要不同的模型时选择阶段路由——用更强的模型设计，用更便宜或更快的模型落实。执行阶段只有两三步时跳过它：换模型会开启一条全新的提供方缓存血脉，短的执行阶段摊不平这笔开销。

### 最小配置

在已有计划模式的组合中挂载此行。路由交给设置段而不内联在这里，因为部署持有哪些模型不是发布的组合能知道的事实。

```yaml
- name: '@deepseek-ai/dsh-plan-mode'
  config:
    section: |
      You are in plan mode. …
- name: '@deepseek-ai/dsh-plan-model-switch'
  config:
    foldPlanning: true
```

| 字段 | 默认值 | 含义 |
|---|---|---|
| `planningProvider` / `planningModel` | （未设置） | 服务计划模式的路由。两者都必填；只填其一则该阶段不路由 |
| `planningReasoningEffort` | （未设置） | 规划路由的适配器推理强度；留空使用模型自身默认值 |
| `executingProvider` / `executingModel` | （未设置） | 计划通过后服务会话的路由，同样遵循要么都填要么都不填 |
| `executingReasoningEffort` | （未设置） | 执行路由的适配器推理强度 |
| `foldPlanning` | `true` | 离开计划模式时，是否把已通过计划背后的探索折叠成一段摘要 |

生成的[配置目录](../../../docs/config-catalog.zh.md#deepseek-aidsh-plan-model-switch)是所有可接受字段及其 JSDoc 的详尽来源。

### 切换什么，何时切换

路由在计划模式自身状态变化的那个步骤边界改变——执行已通过计划的那一步，就已经是执行模型服务的第一步。每次交接都会追加一条持久的 `[model changed: …]` 提示，因此阅读记录的人能分辨哪一段由哪个模型写成。从不进入计划模式的会话保持创建时的模型；未配置的阶段保持当前已生效的路由。

### 折叠做了什么

计划通过时，从计划模式打开的那一刻到承载计划的助手消息之间的 surface 节点，会通过 compaction seam 被替换成一段摘要。已通过的计划、规划之前的对话以及系统提示都在该跨度之外，原样保留。被替换的内容仍留在会话日志中，因此重放能复现被压缩的对话，人也仍然能读到被折叠的部分。

折叠在执行阶段第一步运行之前完成，因此那一步携带的已经是计划而不是探索过程。以下情况会静默跳过折叠，这是刻意设计：部署未组合 compaction 引擎；离开计划模式时没有已通过的计划（`/plan off`）；跨度不足四个 surface 节点；会话在本插件首次看到它之前就已处于计划模式（恢复或 fork）。折叠失败会记录日志，会话继续在执行路由上运行。

## 理解实现

<details>
<summary>实现内部——点击展开</summary>

本节解释本包背后的设计决策；可观察行为已在[使用本包](#use-this-package)中完整覆盖。

### 设计哲学

- **成果物就是交接物。** 执行模型是另一个从未读过探索过程的模型；它拿到的是人批准过的计划。这正是折叠止步于计划之前、而不是把计划连同其余内容一起摘要的原因，也是 `plan-execute` 预设的规划指导要求写出理由与被排除方案的原因。
- **只在转变时路由。** 首次看到一个不在规划中的会话是起始状态而非转变，因此从不规划的会话永远不会被悄悄移到执行模型上。
- **一条路由要么两半都有，要么都没有。** 只填一半会从会话当前选择里解析另一半——那是与用户要求不同的模型。
- **折叠是优化，从不是依赖。** 围绕它的每条失败路径（没有引擎、没有计划、跨度不平衡、compaction 被拒）留下的都是一个运行在正确路由上的正确会话。

### 源码地图

| 文件 | 角色 |
|---|---|
| [`src/index.ts`](src/index.ts) | 插件入口：配置 schema、设置段、阶段边界与路由安装 |
| [`src/routes.ts`](src/routes.ts) | 扁平的分阶段路由形状及其到 `ModelSelection` 的投影 |
| [`src/fold.ts`](src/fold.ts) | 跨度选择：成果物节点，以及它之前那段平衡的规划跨度 |
| — | 不发布运行时不变量伴随文档；除其所属 seam 强制的契约外，本包不暴露独立的事件序列或可变数据关系。 |

### 切换落在哪里

Agent 循环先组装提示词，然后开启 `agent/pre-step` 瀑布——计划模式正是在其中提交自身状态的。本插件在 `next()` 之后读取该状态，因此看到的是这一步即将运行于其下的边界。它安装选择时同时写入 `current` 与已捕获的 `assembled`，因为该步骤的组装已经结束：不这样做，承载已通过计划的那一步仍会跑在规划模型上。请求路由、`{{model}}` 提示词变量与模型变更提示都来自 `dsh-agent` 的 `installModelSelection`，每个 agent 在其自身作用域内安装一次。

### 为什么用位置而不是序号

折叠跨度按 surface 位置计算。位置替换会让可见 seq 变得非单调，因此比较序号就是在比较错误的顺序；对 surface 做 `indexOf` 才是模型实际看到的顺序。

<a id="model-experience"></a>
## 模型体验

### 模型变更提示

#### 模型看到什么

`dsh-agent` 在每次路由变更时追加的持久 user 角色提示，指明边界之上的模型与继续该会话的模型。

#### Token 影响

固定且很小：每次交接一行短文本，一个计划周期最多两次。

#### KV Cache 影响

替换式。阶段切换会为新路由开启一条全新的提供方缓存血脉，折叠则用一段摘要替换先前的请求 token；两者都是有意为之，也都意味着某一阶段的首次请求无法复用任何内容。阶段内部前缀重新变为只追加。

### 被折叠的规划历史

#### 模型看到什么

compaction 引擎的摘要取代探索过程，其后是原样保留的已通过计划。

#### Token 影响

替换式：规划跨度的 token 在此后整个会话中被换成一段摘要。

#### KV Cache 影响

在批准边界发生一次替换；已审阅的计划及其之后的一切保持为稳定前缀。

## 已知限制与延期工作

<a id="known-limitations-and-deferred-work"></a>


这些限制说明阶段路由在哪些情况下与预期不同。

- **切换要付一次冷前缀**——换一个模型无法复用会话的任何提供方缓存。阶段路由在长执行阶段回本，在短执行阶段亏本。
- **交接处 `{{model}}` 提示词变量滞后一步**——提示词在计划模式提交状态之前组装，且没有外部观察者能更早看到那次提交。请求本身路由正确，只有 persona 中指明模型的那一行慢了一步。
- **折叠需要一份已通过的计划**——用 `/plan off` 离开不折叠任何内容，因为被放弃的探索是它自身唯一的记录。
- **摘要由 compaction 引擎自身的路由写成**——发布的引擎用最近一次请求所用的模型做摘要，因此折叠会在那个模型上花掉一次摘要调用。
- **计划模式靠文字约束而非强制**——本包不改变这一点；需要规划阶段只读的部署应独立配置沙箱模式与审批策略。

#### 未来：为摘要调用选路

折叠的摘要由 compaction 引擎解析出的路由写成，而在批准边界上那仍是规划模型。在执行模型上做摘要更便宜；一旦 seam 支持为单次调用指定路由，这就是一个参数的改动。

#### 未来：计划模式之外的阶段

目前的"阶段"概念就是计划模式的两个状态。第三个阶段（评审，或一次验证过程）会需要同样的路由，而 `routes.ts` 与边界观察之间的切分正是它该落脚的地方。
